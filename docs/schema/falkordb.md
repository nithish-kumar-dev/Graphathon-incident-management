# FalkorDB schema v1

FalkorDB is the source of truth for incidents, company knowledge and the agent audit trail. The schema was signed off on 2026-10-18 (`docs/refactor-plan.md` §3, §8).

- **Single source of truth in code:** `apps/api/app/graph/schema.py`. This page describes it; if the two disagree, the code wins and this page is the bug.
- **Server:** `falkordb/falkordb:v4.22.0` (graph module 42200), Python client `falkordb 1.8.0`.
- **What the server supports:** generated by `scripts/probe_falkordb.py` into [`../falkordb-capabilities.md`](../falkordb-capabilities.md).

## Conventions

| Topic | Rule |
|---|---|
| Graph | One graph, `graphathon` (`GRAPH_NAME`). Tests use their own throwaway graphs on a separate server (see the known server issue below) |
| Tenancy | Every domain node carries `tenant_id` and `env`, and every edge carries `tenant_id`. Every repository query filters on both, and edges cannot cross tenants. All tenants in this repo are synthetic: `nova` is NovaCommerce, `acme` is a test-only decoy |
| IDs | `id` on every label, **globally unique**, enforced by a unique constraint per label. Seed IDs are tenant-prefixed slugs such as `nova.svc.checkout`; runtime IDs will be a prefix plus a ULID. Human keys such as `INC-101` go in `key`, external references in `source_ref` |
| Time (UTC policy) | Every timestamp is `*_at_ms`: an **integer in epoch milliseconds, UTC**. The server has no `datetime()` function, but it does have `localdatetime()`, `date()` and `duration()`; integers are portable and range-indexable. The API converts to and from ISO-8601 with `Z`. Writes with a non-integer `*_at_ms` value are rejected |
| System properties | `id`, `tenant_id`, `env`, `created_at_ms`, `updated_at_ms` and `schema_version` are set by the repository only. Callers may also set `source` (seed/ingest/agent/human) and `source_ref` |
| Arrays | Stored as native array properties: `roles`, `allowed_action_types`, `provenance_refs` |
| Query safety | Labels, relationship types and property keys come only from the allowlists in `schema.py`. Values always go in as parameters. Path depth is a validated integer from 0 to 3 written into the query text, because the server rejects `*1..$d` |

| Alert | fingerprint, severity, fired_at_ms | severity critical/warning/info; summary_redacted |
| **Evidence** *(new)* | kind, source_ref, observed_at_ms | kind metric/log/deploy_event/alert/ticket/doc; excerpt_redacted; content_hash |
| TimelineEvent | at_ms, type | actor, summary, ref_id |
| Service | name | tier |
| Team | name | |
| Responder | handle | roles (e.g. `approver:payment`); synthetic handles only, no PII |
| Deployment | version, deployed_at_ms | status |
| Runbook | title, version | uri, allowed_action_types |
| Decision | title, statement, status, effective_from_ms | A policy or ADR, **not** an agent conclusion. status active/superseded; effective_to_ms; required_approver_role |
| Document | title, doc_type | doc_type adr/policy/postmortem/runbook; uri; classification public/internal/confidential/restricted; body_redacted (Phase 3, chunked for retrieval) |

| **ApprovalRecord** *(new)* | decision, spec_hash, action_version, approver_id, decided_at_ms | decision APPROVE/REJECT/REQUEST_REVISION/ESCALATE; expires_at_ms; policy_decision_id |
| AgentMemory | memory_type, verification_status, outcome, summary | episodic/procedural; draft/verified/rejected/superseded; successful/failed/unknown; provenance_refs; validated_at_ms; validation_method human/ground_truth (Phase 3); embedding properties (below) |
| **AgentEvent** *(Phase 5, migration v0003)* | kind, status, at_ms, revision, detail | One orchestrator step transition (`started` / `completed` / `failed` / `skipped` / `waiting`). Idempotent id; `PART_OF` its AgentSession. Read in causal order by `GET /api/investigations/{id}/events` |
| SchemaMigration | (written by the migration runner) | version, name, checksum, applied_at_ms. Not tenant-scoped |

**Additive properties (Phase 2, no migration needed):**

- `Alert`: `service_id`, `dedup_count`, `last_fired_at_ms`, `dedup_source_refs` (at most 50)
- `AgentSession`: `retrieval_json` (Phase 5: the retrieval snapshot used by the run, capped at 400,000 characters), `branch_status_json`, `requested_by`, plus the status enum `queued` / `running` / `awaiting_review` / `completed` / `failed` / `escalated` / `inconclusive` / `timed_out`

`schema_version` stays 1, because older nodes remain valid.

**Embedding properties (Phase 3, `DocumentChunk` and `AgentMemory`):** `embedding` (native `vecf32`), `embedding_model`, `embedding_version`, `embedding_dim`, `embedded_hash`.

- They are written only by `GraphRepository.set_embedding`, which checks the dimension and finiteness. `merge_node` and `update_node` reject them.
- The repository strips `embedding` from every read result.
- FalkorDB stores a vector of the wrong dimension without error, so the application checks every vector (`docs/retrieval.md`).

### Memory verification state machine (Phase 3)

```
(none) --create_draft--> draft/unknown --validate_by_human | validate_by_ground_truth--> verified/{successful|failed}
                         draft --reject--> rejected
                         verified --supersede (new memory -[:SUPERSEDES]-> old)--> superseded
```

- **One write path.** `verification_status`, `outcome`, `validated_at_ms` and `validation_method` change only in `app/services/memories.py`, through the named query `set_memory_verification`.
- **Generic writes are guarded.** `merge_node` creates an `AgentMemory` only as `draft`/`unknown`, and sets these properties only on creation, so a re-seed never downgrades. `update_node` rejects them.
- **Verified** requires all of:
  - at least one `GROUNDED_IN` Evidence node, and
  - either a `VALIDATED_BY` Responder (`validation_method: human`) or observed-outcome evidence (metric/ticket/log, not before the incident started; `validation_method: ground_truth`), and
  - every `DERIVED_FROM` action `executed_simulated`. A proposed fix is never verified.
- **Failed outcomes are kept.** The seed holds one verified *failed* memory (restarting checkout didn't help) so that agents don't repeat that action.
- **Seeding.** Seed memories are created as drafts and verified by the loader through `validate_by_human` (`VALIDATIONS` in `novacommerce.py`). That call is idempotent and also back-fills `validation_method` and `VALIDATED_BY` on memories verified before Phase 3.
- **Integrity.** `integrity_unvalidated_verified_memory` flags a verified memory with no grounding, with no validator and no ground truth, missing `validation_method` or `validated_at_ms`, or derived from an unexecuted action.

## Relationships

The Phase 1 list, verbatim, followed by the three additions approved at sign-off and the Phase 3 `HAS_CHUNK`. Direction matters, and the names are identical everywhere.

```
(Incident)-[:HAS_ALERT]->(Alert)                 (AgentAction)-[:SUPPORTED_BY]->(Evidence)
(Incident)-[:HAS_EVIDENCE]->(Evidence)           (AgentAction)-[:TARGETS]->(Service)
(Incident)-[:AFFECTS]->(Service)                 (AgentAction)-[:PART_OF]->(AgentSession)
(Service)-[:DEPENDS_ON]->(Service)               (AgentAction)-[:HAS_REVIEW]->(ApprovalRecord)
(Deployment)-[:DEPLOYED_TO]->(Service)           (AgentMemory)-[:ABOUT]->(Incident)
(Team)-[:OWNS]->(Service)                        (AgentMemory)-[:DERIVED_FROM]->(AgentAction)
(Responder)-[:MEMBER_OF]->(Team)                 (AgentMemory)-[:GROUNDED_IN]->(Evidence)
(Decision)-[:GOVERNS]->(Service)                 (AgentMemory)-[:VALIDATED_BY]->(Responder)
(Decision)-[:DOCUMENTED_IN]->(Document)          (AgentMemory)-[:SUPERSEDES]->(AgentMemory)
(Decision)-[:SUPERSEDES]->(Decision)             (Document)-[:RELATES_TO]->(Service)
(Runbook)-[:APPLIES_TO]->(Service)               (Document)-[:RELATES_TO]->(Incident)
(Evidence)-[:OBSERVED_ON]->(Service)
(Evidence)-[:REFERS_TO]->(Deployment)

Approved additions (O5):
(Incident)-[:HAS_EVENT]->(TimelineEvent)
(AgentSession)-[:INVESTIGATES]->(Incident)
(ApprovalRecord)-[:DECIDED_BY]->(Responder)
(AgentEvent)-[:PART_OF]->(AgentSession)          (Phase 5)

Phase 3 addition (approved with RAG):
(Document)-[:HAS_CHUNK]->(DocumentChunk)
```

The repository rejects any other `(source, type, target)` triple, including a reversed direction, before a query is sent. The test `test_reversed_or_unknown_edges_rejected` covers this. `DocumentChunk` and `HAS_CHUNK` arrived in Phase 3 with migration 0002.

## Indexes and constraints: migration `0001_schema_v1`

The spec is in `apps/api/app/graph/migrations/v0001_schema_v1.py`.

| Kind | On | Why |
|---|---|---|
| Range + **unique constraint** | `id` on all 16 labels, including SchemaMigration | MERGE and point lookups; duplicate prevention |
| Range | Incident tenant_id, status, started_at_ms · Alert fingerprint, fired_at_ms · Deployment deployed_at_ms · Decision status · AgentMemory verification_status · AgentAction spec_hash, proposal_id · AgentSession thread_id | Hot lookups only |
| Full-text | Runbook.title, Document.title | Phase 3 keyword fallback |
| Vector | *none in 0001* | Added in 0002 once the embedding dimension was measured. **Note:** the server accepts vectors of the wrong dimension without error (probe), so dimensions must be checked in application code |

Resulting objects: 29 indexed (label, property) pairs and 16 operational unique constraints.

The 0001 list of labels is a frozen literal, not derived from `schema.LABELS`, so its recorded checksum stays `64a83edec4ecf5b757def0209392a9bc23f6d274f06a239b51567c6944595299`.

## Indexes and constraints: migration `0002_hybrid_retrieval` (Phase 3)

The spec is in `apps/api/app/graph/migrations/v0002_hybrid_retrieval.py`. It only adds objects.

| Kind | On | Why |
|---|---|---|
| Range + **unique constraint** | `DocumentChunk.id` | Idempotent chunk upserts |
| Range | `DocumentChunk.document_id` | Chunks per document |
| Full-text | `DocumentChunk.text_excerpt`, `AgentMemory.summary` | Keyword step of retrieval |
| Vector | `DocumentChunk.embedding`, `AgentMemory.embedding`: dimension **768**, cosine (HNSW M 16, efConstruction 200, efRuntime 10 are server defaults) | Vector step. 768 is the measured output of `nomic-embed-text` via Ollama 0.19.0 |

After 0002: 35 indexed (label, property) pairs and 17 operational unique constraints.

- **Checksum.** The checksum includes a `vector` key only when a migration declares vector indexes, so 0001's recorded checksum did not change.
- **Vector index mismatch.** If a vector index already exists with another dimension or similarity function, the runner aborts. A different embedding model needs a new migration.
- **Full-text and vector indexes are graph-wide** (all tenants). Queries filter candidates by tenant after the lookup; production should use one graph per tenant (`docs/retrieval.md`).
- **Missing indexes return nothing.** A full-text query on a missing index returns no rows rather than an error, so retrieval checks `db.indexes()` and reports `keyword: failed` until 0002 is applied.

## Migration notes

The runner is `apps/api/app/graph/migrate.py`, invoked via `scripts/migrate_graph.py`.

- **Idempotent.** The runner introspects `db.indexes()` and `db.constraints()` and creates only what is missing; the server errors on duplicate creation. A second run reports `applied=[] skipped=[1, 2] created=0`.
- **Recorded.** Each applied migration leaves `(:SchemaMigration {id:'schema_migration.0001', version, name, checksum, applied_at_ms})`.
- **Checksummed.** If a recorded migration's spec changes, the runner aborts. Never edit an applied migration; add the next `v000N_…` module and append it to `MIGRATIONS`.
- **Constraints after dedupe.** A unique constraint is created only after `integrity_duplicates` returns zero for that label. The runner then waits until the constraint is `OPERATIONAL`, because creation is asynchronous.
- **Locked.** Redis key `graphathon:migration_lock:<graph>` (SET NX, 120s TTL) stops concurrent runners.
- **Rollback.** `migrate_graph.py --down N --confirm <graph>` is dev only. It drops exactly what migration N declares, then **immediately rewrites the AOF** (see below).

## Known server issue: AOF replay segfault after a unique constraint is dropped

This affects FalkorDB 4.22.0 and 4.22.1.

**What happens.** A unique constraint is removed, either with `GRAPH.CONSTRAINT DROP` or by `GRAPH.DELETE` of a graph that has one. Later the server restarts and the AOF is replayed more than once. Redis then segfaults in `GraphContext_GetSchemaByID` while replaying `GRAPH.EFFECT`, and the container crash-loops.

- Found on 2026-10-18, when the test suite deleted constrained test graphs on the dev server.
- Reproduce it with `scripts/repro_falkordb_aof_crash.sh [image]`, which uses a throwaway container. Exit 1 means the bug reproduced.
- The original crash log and the poisoned AOF are kept in `backups/falkordb-poisoned-20261018T094646Z/`.

**What does not trigger it** (verified):

- `DETACH DELETE` of nodes, which is what `scripts/reset_graph.py` does
- graphs with only range indexes
- deleting graphs that have no constraints
- `EFFECTS_THRESHOLD` set very high: this does *not* help

**Rules we follow:**

1. Never drop a unique constraint, or delete a constrained graph, on the persistent `falkordb` service. The app and the seed never do either.
2. The test suite runs only against the ephemeral `falkordb-test` service (AOF off, no snapshots, tmpfs). `tests/conftest.py` refuses to start against any server with persistence enabled.
3. `migrate --down` runs `BGREWRITEAOF` immediately after dropping. Compacting the AOF removes the poison; this was verified over three restart cycles.
4. Before upgrading the image, run the reproduction script against the new tag. Relax these rules only when it exits 0.

**Recovery if a server is already crash-looping:**

1. `docker compose stop falkordb`.
2. Copy the volume out: `docker run --rm -v graphathon_falkordb_data:/src:ro -v "$PWD/backups/x":/dst alpine cp -a /src/. /dst/`.
3. Restore, by either:
   - wiping the volume and running `migrate_graph.py` then `seed.py` (all data here is reproducible), or
   - starting once with `--appendonly no` to load `dump.rdb`, then `CONFIG SET appendonly yes` so Redis writes a clean AOF.

Both are destructive to the volume, so get approval first.

## Cypher behaviour to remember

- **No relationship uniqueness within a pattern.** `(i)-[:AFFECTS]->(s)<-[:AFFECTS]-(o)` can bind `o = i` by reusing the same edge. Standard Cypher forbids this. Queries that walk out and back must deduplicate explicitly (`WITH DISTINCT`), as `incident_memories.cypher` does.
- **One write per graph at a time.** Each write query executes atomically. Ingest relies on this: dedup, alert creation and attach-or-open are each a single query.
- **`FOREACH (_ IN CASE WHEN … THEN [1] ELSE [] END | CREATE/MERGE/SET …)`** is the conditional-write idiom, verified on 4.22.0.

## Golden evidence path (NovaCommerce INC-101)

This is real output from the seeded graph, via `GraphRepository.rollback_candidates('nova.inc.101')`:

```
nova.inc.101 -[AFFECTS]-> nova.svc.checkout -[DEPENDS_ON]-> nova.svc.payment
nova.dep.payment.v2_4 -[DEPLOYED_TO]-> nova.svc.payment
nova.inc.101 -[HAS_EVIDENCE]-> nova.ev.101.deploy -[REFERS_TO]-> nova.dep.payment.v2_4   (synthetic://deploys/payment/v2.4)
nova.dec.payment.rollback_v2 (active, ADR-031) -[GOVERNS]-> nova.svc.payment   => required approver role: approver:payment
nova.rb.payment.rollback -[APPLIES_TO]-> nova.svc.payment
```

A deployment is a candidate only when it targets a service within 3 `DEPENDS_ON` hops of an affected service **and** the incident's own evidence refers to it. Inventory v1.9 is reachable but has no evidence, so it is excluded.

**What changes the recommendation.** Both cases are asserted in `tests/test_golden_path.py`:

| Mutation | Result |
|---|---|
| Delete `nova.svc.checkout -[DEPENDS_ON]-> nova.svc.payment` | No candidates; the v2.4 rollback recommendation disappears. Restoring the edge brings it back |
| Delete `nova.dec.payment.rollback_v2 -[GOVERNS]-> nova.svc.payment` | Still a candidate, but `active_decision_ids = []` and no required approver. The superseded v1 policy does **not** come back, so Phase 5 must escalate |
| Evaluate at 2026-05-01, before ADR-031 took effect | No active policy in force |
